给小网站加搜索：先明确用户找什么

给个人网站加搜索，听起来像是一个很自然的升级：文章多了，页面也多了，总该让人输几个字就找到答案。但真正动手以后，我发现最容易被忽略的不是搜索框怎么摆，而是“访客来这里到底想找什么”。没有先想清楚这个问题，很容易做出一个看起来完整、实际几乎没人使用的功能。

我曾把所有文章标题、正文和标签都塞进索引，搜索页第一次打开时很有成就感。后来自己试着找一篇旧笔记，输入“日期”，结果排在最前面的是几篇只在代码示例里出现过这个词的文章；真正想找的 dayjs 笔记反而要往下翻。那一刻才明白，搜索不是把文字堆起来，而是替读者缩短“我脑子里想到的词”和“站里实际写的词”之间的距离。

先把搜索问题写下来

小网站的搜索需求通常没有想象中复杂。可以先翻一遍最近的留言、朋友问过的问题，或者自己回忆一下重开旧项目时最常找什么。对技术博客来说，常见的不是“给我一篇包含某个字的文章”，而是下面几类问题：

  • 我记得写过一个主题，但忘了标题，例如“接口超时怎么处理”。
  • 我想找同一类内容，例如所有和 Git、发布、CSS 有关的文章。
  • 我只记得一段很具体的词，例如某个报错、库名或命令。
  • 我想知道站里有没有写过某件事，而不是一定要看全文。

这几类问题决定了搜索要优先匹配什么。标题、分类、标签应当比正文更靠前；正文匹配可以保留，但不要把一段代码中的偶然字符串当成强结果。若文章数量不到几十篇，清楚的分类页、标签页和归档页已经能承担一部分“找内容”的工作，搜索不是一定要抢走它们的角色。

一个很实用的做法是给每篇新文章补一行“读者可能会怎样搜到它”。例如写静态站部署时，除了“静态站”，还可能有人搜“博客发布”“GitHub Pages”“域名解析”。这些词未必要硬塞进正文，可以落在标签、摘要或文章开头的自然句子里。这样做不是迎合机器，而是在给未来的自己留路标。

先选够用的方案，不急着上服务

我把站内搜索大致分成三个层次。第一层是页面内筛选：把文章标题和标签加载到浏览器里，输入后即时隐藏不匹配的卡片。它适合文章很少、希望零配置的站点，优点是简单，缺点是无法全文检索。

第二层是静态索引。构建网站时生成一个 JSON 或 XML，把标题、链接、日期、摘要、标签和一小段正文放进去；浏览器下载索引后在本地查找。多数个人博客到了这个阶段就足够了：没有额外账号，没有服务端费用，更新文章时也会自动更新索引。代价是文章非常多时，首次加载会稍重一些。

第三层才是外部搜索服务或自建搜索引擎。它能处理拼音、同义词、排序、拼写纠正甚至分析访问数据，但也带来密钥、隐私、费用和维护。除非站点内容规模很大，或确实需要“搜索是核心功能”，否则不必为了一个放大镜图标背上另一套系统。

选择方案前，我会问三个小问题：索引文件会不会让首屏变慢；搜索结果能不能直接跳到文章；断网或服务异常时，页面是否仍然正常阅读。能答上来，方案通常就不会离实际太远。

静态搜索的最小实现思路

如果使用静态站生成器，搜索并不神秘。构建时收集每篇文章的元信息，生成类似下面的记录：标题是“处理日期和时区时，别相信看起来没问题”，标签有“日期、时区”，链接指向文章页，摘要只保留一两段。页面加载后，把用户输入转换为小写、去掉两侧空格，再依次比较标题、标签和摘要。

排序可以很朴素：标题命中排第一，标签命中排第二，摘要命中排第三；同一层里再按发布时间倒序。不要急着发明复杂的相关度公式。对于几十到几百篇文章，这样的规则很容易解释，也容易在出现奇怪结果时调整。

结果列表要给出足够的线索：标题、日期、分类、命中的摘要片段和可点击的文章链接。只显示标题会让人反复点开再返回；整篇正文都展示又会让页面像一堵墙。摘要中把命中的字轻微高亮即可，颜色不要只靠红绿区分，键盘焦点也要看得见。

上线前我会这样试一遍

写完功能后，别只搜一次文章标题就宣布完成。我通常拿一张小纸条列出十个词：精确标题、常见简称、一个标签、一个正文词、一个不存在的词、带空格的词、英文大小写不同的词、中文标点附近的词、只命中旧文章的词，以及手机输入法下的一次搜索。每一个都看三件事：有没有结果、第一条是不是合理、点进去是否正确。

还要刻意测试空状态。输入“火星技术”时，页面不该只留一大片空白，可以说“没有找到相关内容”，再给出分类页或归档页链接。搜索框清空后应立即恢复全部列表；按回车时不应莫名刷新页面；移动端键盘弹出后，结果最好仍在可见范围内。

最后检查构建产物里的索引。它不应包含草稿、私密文章、环境变量或不想公开的备注。静态文件一旦发布就是公开内容，这一点比搜索做得多聪明都重要。

搜索是一条回来的路

一个个人站最常使用搜索的人，往往就是作者自己。几年后你可能只记得“我好像记过这个坑”，却想不起文章标题。好的搜索不会显得炫耀，它只是安静地把那条旧路重新照亮。

因此先把标题写清楚、分类和标签维护好，再用一套简单可预测的搜索把它们连起来。等真正出现“用户总在搜但搜不到”的证据，再升级同义词、拼音或外部服务。功能可以慢慢长，读者找到内容时那种少绕一步的轻松感，才是搜索最值得保留的部分。
