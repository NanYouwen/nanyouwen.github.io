静态网站的更新流程：从写文章到发布

静态网站给人的第一印象是省心：没有后台服务，不用担心数据库迁移，写完文章、执行构建、把生成文件推上去，事情似乎就结束了。真正维护一段时间以后才会发现，麻烦通常不在某一条命令，而在命令之间那几分钟。图片有没有放对位置？草稿会不会被一起发出去？文章里的旧链接还通吗？发布之后发现问题，怎么从容地回到上一版？

我以前把更新理解成“最后一次 push”。结果有过一次文章在本地预览很好，线上却少了一张图；原因只是文件名里一个大小写不一致，Windows 本地没暴露，部署环境却严格区分。那次之后，我开始把更新当成一条小流水线。它不追求复杂自动化，只是让每一步都有明确的输入和一个可以检查的结果。

写作阶段先把素材放到该在的位置

一篇文章开始时，我会先建好 Markdown 文件、确定标题和日期，再决定图片和附件的路径。图片不建议散落在桌面或临时下载目录里，因为三周后再改文章时，很难判断哪一张是最终版本。可以按文章短名建立资源文件夹，或统一放到站点约定的图片目录，并使用相对路径引用。

写正文时有两个小习惯很省事。第一，链接尽量写成有意义的文字，而不是一长串地址；第二，外部信息若带有时效性，就在句子里写明“截至何时”。后者尤其适合工具、价格、版本和政策类内容，读者以后看到不会误以为它仍是今天的状态。

文章完成后，不要立刻打开浏览器检查排版。先在编辑器里做一次安静的阅读：标题是否过长，二级标题能不能概括段落，代码块有没有漏掉语言标记，图片有没有替代文本，示例里的账号、令牌或真实地址有没有被不小心贴进去。这个阶段发现的问题，修起来最便宜。

本地预览不是形式，它负责发现语境问题

接下来启动本地预览。它和直接读 Markdown 的差别很大：主题样式会影响标题层级，长链接可能撑破手机宽度，表格在窄屏上可能不好看，文章摘要截断的位置也可能很奇怪。我会至少看三个位置：文章首页、归档或分类页、手机宽度下的正文页。

预览时可以采用“从入口走到出口”的方式，而不是只停在新文章上。先从首页点击文章，再查看上一页和下一页、标签链接、目录锚点、文末链接，最后返回首页。这条小路线能顺手发现错别字以外的许多问题，比如分类名称不一致、永久链接重复、导航高亮失效。

如果站点依赖生成搜索索引、RSS 或 sitemap，也要确认它们会随着新文章更新。很多问题不是文章页坏了，而是读者通过搜索、订阅或搜索引擎找不到它。开发环境里做一遍检查，比发布后等人提醒舒服得多。

构建前做一次“只看变化”的检查

我习惯在构建前看一眼版本控制的改动列表。目的不是追求提交得漂亮，而是确认这次更新只带了该带的东西。常见的意外包括本地缓存、编辑器备份文件、测试截图、刚才为了排错改过却忘了还原的配置，以及不该公开的草稿。

一个很轻的发布清单可以是：

  • 新文章的日期、分类、标签和链接是否正确；
  • 图片、下载文件是否已被版本控制追踪；
  • 站内链接和主要外链是否能打开；
  • 没有把草稿、私密笔记或密钥放入本次改动；
  • 当前分支是否是预期的发布分支；
  • 如需回退，上一版的提交或构建产物在哪里。

这几项不需要每次写成文档，贴在项目 README 或命令行备注里就够。清单的价值不是消灭错误，而是在赶时间时替人保留一点次序感。

构建产物要像用户一样检查

执行构建后，别因为命令没有报错就直接部署。生成器能成功，不代表结果一定正确。最实用的是用一个干净的本地服务打开构建目录：确认新文章存在，资源路径没有 404，中文路径和大小写正常，搜索与归档里也能找到它。

如果站点有压缩、缓存或 CDN，构建后的文件名和缓存策略也值得看一眼。内容更新后仍看到旧页面，有时并非部署失败，而是浏览器或 CDN 还在使用旧缓存。不要一上来就清所有缓存；先确认页面 HTML 的更新时间、新文件是否上传，再决定是否需要更精确的刷新。

部署完成后的验证应该短而明确。用无痕窗口或手机网络打开首页，进入新文章，点一条内部链接，确认 HTTPS、图片和样式正常即可。若有监控或构建日志，看一眼是否出现异常。验证完成再通知朋友或贴到社交平台，可以避免把“刚发现还在修”的链接发出去。

给回滚留一个普通人也会用的入口

静态站很适合回滚，但前提是你知道回到哪里。源码仓库要保留可构建的版本，部署仓库或托管平台要能找到上一版发布记录。对于纯内容更新，最稳妥的做法是每次发布对应一个清晰提交；一旦文章有严重错漏，先回退到前一版，再慢慢修，而不是在线上临时改多个文件。

小站不需要把自己变成大型发布平台。写作、预览、检查变化、构建、部署、线上验证这六步已经足够覆盖大多数风险。流程固定下来以后，更新不再像一次冒险，而更像每隔几天给房间开一次窗：动作不多，但会让整个站点一直有空气。

把发布后的反馈也接进流程

发布不是内容生命周期的终点。文章上线后的头一天，我会再从站外入口打开一次：例如搜索结果、订阅链接或朋友转发的地址。这样能发现带参数访问、分享卡片、缓存和移动浏览器下才会出现的细节。若文章有勘误或补充，也不要为了保持“完美”悄悄改掉重要结论；可以在文末写明更新说明，让读者知道信息何时变化。

对于长期维护的站点，还可以给每次发布留一个很小的记录：本次新增了什么、是否改过主题或配置、构建是否有警告、需要以后再看的问题是什么。它既不是繁琐工单，也不是给自己增加负担。三个月后重新打开项目时，这几行字会告诉你上一次离开时站点是什么状态。流程之所以值得保留，不是为了让每次更新更庄重，而是为了让下一次回来时，能从一个清楚的位置继续。
