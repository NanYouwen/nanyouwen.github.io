用 Lighthouse 看网页，不被分数绑架

第一次打开 Lighthouse 报告时，很容易被那个圆形分数吸住。九十多分让人松一口气，六十多分像收到一句批评，于是开始追着每一条红色提示改：把图片再压一点、把脚本再拆一点、把字体再晚一点加载。工具确实很有帮助，但如果把分数当成唯一目标，最后可能得到一个“测试环境很漂亮、真实读者却不舒服”的页面。

我更愿意把 Lighthouse 当作体检报告，而不是考试成绩。体检报告提醒你哪里值得看一眼，却不能替你判断今天该不该跑步。网页也是一样：它提供性能、可访问性、最佳实践和 SEO 的线索，真正要回答的仍是用户能否尽快看见主要内容、能否顺利点击和阅读、遇到网络波动时会不会无助地等着。

先知道它在测什么

Lighthouse 会在模拟环境中加载页面，并根据一组指标给出建议。性能部分常见的几个词不必背定义，先把它们翻成体验语言就够了：页面主要内容什么时候出现；最大的视觉元素什么时候稳定；用户第一次点按钮时页面会不会卡住；布局有没有在加载中突然跳动。

报告的环境不是每位真实用户的手机和网络，但它很适合发现趋势。连续几次报告都说首屏图片过大，通常值得处理；某次分数突然下降二十多分，则可能意味着最近的改动带来了回归。反过来，某一项因为实验环境波动而上下跳几分，不值得让人一整天围着它转。

我通常先确认测试入口一致：同一个 URL、相近的网络条件、没有登录态干扰，必要时做两三次取中间结果。首页、文章页、最常用的功能页分开看，因为它们的瓶颈往往不同。只测首页得出“整个站都很快”，和只看一次体检就说身体没问题一样仓促。

报告里优先看能让人少等的事

面对一长串建议，可以先按影响程度分三类。第一类是用户明显能感到的问题，例如首屏大图没有尺寸导致正文跳动、关键接口卡住后没有反馈、主线程被一大段脚本占满。这些应该优先解决，因为用户真的会因此退出或重复点击。

第二类是能带来稳定收益的改动，例如压缩过大的图片、删除没有使用的资源、给静态文件合理缓存、延后非关键的第三方脚本。它们通常不需要推翻页面结构，适合放进正常迭代。第三类才是微调：为了再多一两分而牺牲可读字体、首屏信息或交互方便的改动，可以先停下来问一句，分数提高以后，谁真的得到了好处？

例如报告提示图片体积过大，正确的第一步不是一律把图片压到最小，而是看它出现在哪里。文章正文里的插图允许稍后加载；首页头图是关键内容，应该在清晰度和加载速度之间取平衡。若图片上包含文字或代码，过度压缩会让人看不清，反而把问题从网络转移到了阅读。

用一条真实页面做小实验

假设一篇文章页打开慢，报告里显示最大内容元素是一张封面图。可以先查看原图的实际像素和文件大小：如果页面只展示宽一千像素，上传的却是四千像素原图，先导出合理尺寸的 WebP 或压缩后的 JPEG，再保留一份原图在素材库里。接着给图片写明宽高，减少加载完成前的版面跳动。

改完后重新测一次，同时用手机真实打开页面。若首屏确实更快、文字依然清晰，这个改动就有价值。若分数提升不多但用户体验变好，也值得保留；若分数好看了却让封面模糊、让文章开头空白更久，就应当回头调整。工具负责提供证据，人负责做取舍。

同样的方法适合脚本。报告说有未使用 JavaScript 时，先找它属于哪个功能：是评论、统计、搜索还是主题插件？如果它只在少数页面使用，可以按需加载；如果删掉会让主要功能不可用，就不要为了一条提示贸然移除。改动之前记下基线，改动之后验证功能，能回滚比“这次终于满分”更重要。

别忘了可访问性和日常细节

Lighthouse 的性能分数最醒目，但另外几项也很实在。图片替代文本、按钮名称、标题层级、颜色对比度，这些往往只需一点整理，却能帮助键盘用户、屏幕阅读器用户和网络不稳定的读者。SEO 建议里的标题、描述、可索引性，也是在帮未来通过搜索来到页面的人少走弯路。

不过工具无法替你判断文字是否好懂、表单提示是否礼貌、广告或弹窗是否打扰。它也不会知道一篇长文最有价值的图是不是应该优先展示。因此每次看报告，我会顺手完成三件事：用键盘 Tab 走一遍关键按钮；把页面缩到手机宽度看一眼；找一位没有参与开发的人试着完成主要任务。真实的停顿和疑问，比一条抽象指标更有说服力。

把分数放回它该在的位置

性能优化是长期维护，不是一次冲刺。建立一张简单记录就够：日期、页面、主要指标、这次改了什么、结果如何。以后出现回归时，你能看出变化从哪里开始；新功能上线前，也能知道是否影响了关键页面。

分数当然值得参考，但它不是网站的目的。一个加载及时、内容清楚、可被不同人顺利使用的页面，即使没有把每个圆环刷到极致，也已经完成了大部分该完成的事。把 Lighthouse 当成耐心的同事：它指出风险，你决定先解决哪一个，这样用起来才不会累。

给关键页面留一条朴素的底线

比起追逐某一次满分，我更愿意为少数关键页面设性能预算：首页不能因为新增一张大图就明显变慢；文章正文应尽快可读；提交页在普通网络下要给出及时反馈；部署后不能突然出现大量资源失败。预算可以是大致的资源体积、主要指标区间，也可以只是“改动前后必须在同一环境对比一次”。它的意义是提醒团队：性能是需求的一部分，不是最后有空才做的装饰。

如果某个优化需要牺牲内容或可用性，先把取舍写出来。例如延后加载评论脚本可能让正文更快，但评论区第一次打开会晚一些；替换字体可能减少体积，却影响品牌感。没有绝对正确的答案，重要的是让选择可解释、可回看。Lighthouse 给的是一面镜子，真正要维护的是读者打开页面时的感受，而不是镜子里的一个数字。
