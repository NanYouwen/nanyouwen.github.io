第一次写自动化测试：从最易坏的流程开始

第一次给项目加自动化测试时，很容易卡在两个极端：要么觉得什么都该测，于是还没写第一条就被工具、框架和覆盖率压住；要么觉得页面一改测试就坏，索性继续靠手点。其实一条真正有用的测试，不需要证明系统完美，它只要替你守住一条每次发布都担心会坏的用户路径。

我通常会从“如果它坏了，用户马上走不下去”的地方开始。登录、提交表单、下单、上传文件、保存资料，都比一个纯展示卡片更值得先测。它们往往涉及输入、网络请求、权限、跳转和错误提示，也是手工回归时最容易漏掉步骤的地方。

先选一条短而完整的路

以登录为例，不要一开始测试所有登录方式、所有浏览器和所有权限。先固定一个测试账号，做一件清楚的事：打开登录页，输入账号密码，点击提交，看到首页上的用户名。这样一条测试有明确起点、明确动作、明确成功信号。它失败时，你知道用户在主路径上被卡住了；它成功时，至少说明最基本的一道门还开着。

选路径时可以问三个问题：它是否高频？它失败后是否没有替代方案？它是否经常因为改动而被影响？三项里占两项，就很适合作为第一条。不要为了方便，先测一个永远不会变的静态标题；那样测试绿得很开心，却没有替你挡住风险。

测“用户看见的”，少测实现细节

自动化测试最脆弱的原因之一，是它依赖了页面内部结构。比如用第七个 div、某个样式类名、动画结束时间来定位元素，一旦设计调整，功能没坏测试却全红。更稳的方式是给关键输入和按钮使用稳定、可读的标记，例如 data-testid="login-submit"，或根据可访问性名称找到“登录”按钮。

断言也尽量站在用户角度。与其断言某个组件内部状态变成 true，不如断言页面出现了欢迎语、地址栏跳到预期路径、提交按钮恢复可点击。实现可以重构，用户体验不该随意改变。测试描述的正是这份对外承诺。

别跳过失败路径

只有成功路径的测试像只检查门能不能打开，却没检查钥匙不对时会不会把人锁在里面。为第一条关键流程至少补两个分支：输入错误时有没有清楚提示；网络失败时是否能重新尝试、按钮是否不会永久加载。它们不需要模拟所有服务器异常，只要覆盖用户最能感知的失败方式。

测试数据也要独立。不要使用某个同事的真实账号，也不要依赖一份每天变化的线上数据。准备固定的测试账号、测试记录和初始化步骤，必要时每次运行前创建、运行后清理。这样失败才更可能说明代码问题，而不是环境今天心情不好。

让它跑得稳定一点

浏览器测试最常见的假失败来自等待。页面还没加载完，测试就去点击；接口偶尔慢一点，断言已经开始；多个测试共用同一条数据，前一个修改影响了后一个。解决思路不是无脑加十秒等待，而是等一个真正表示“准备好了”的条件，例如按钮可点击、列表出现、加载提示消失。

每条测试还应尽量只验证一个故事。登录失败和个人资料保存最好分开；这样失败日志短，维护者也能快速定位。运行时间不必一开始追求极限，但不要让十条基础测试花半小时，否则大家会自然地绕开它。

一个可以从今天开始的顺序

  1. 写下最怕坏的一条用户路径和成功标志。
  2. 准备不依赖个人数据的测试账号或数据。
  3. 用稳定标记定位关键控件，不绑定样式结构。
  4. 先实现成功路径，再补一个错误提示和一次网络失败。
  5. 把测试接到提交前或发布前，让它真的被运行。

自动化测试不是取代人工体验。它更像一个不嫌烦的同事，每次改完都帮你确认那条重要道路还通着。当最易坏的几条路先被守住，再慢慢扩展范围，测试才会成为项目的安全感，而不是额外负担。

失败时，让测试告诉你下一步

一条测试失败后，最没用的信息是“超时了”。尽量让它留下页面截图、当前地址、关键网络请求和可读的步骤名称。例如“登录后等待用户名出现”比“第 42 行断言失败”更能帮助半天后接手的人。很多测试框架都能保存这些信息，不必一次配置得很花哨，但至少要让失败可复看。

也要区分产品缺陷和测试不稳定。若同一条在没有代码改动时偶尔失败，不要长期靠重新运行掩盖；记录发生条件，检查等待逻辑、共享数据和外部依赖。测试偶发变红会很快消耗团队的信任，最后大家只会习惯性点击忽略。稳定性本身，就是自动化测试需要维护的功能。

当主路径积累到几条后，可以给它们一个简单的分组：每次提交跑最短的一组，每天或发布前跑完整的一组。这样既不会拖慢日常节奏，也能让真正重要的保障持续发生。测试不需要一下子覆盖整个世界；它只要每次都可靠地守住已经承诺的那几条路，就已经很有价值。

刚开始时，也可以把一次手工回归过程录成最简单的步骤表，再从里面挑最稳定、最重要的两三步自动化。这样测试不会脱离真实使用，而是从团队已经在做的检查里长出来。每补上一条，下一次发布就少一次重复点击，这就是最直观的回报。

测试名称也尽量写成用户故事，而不是实现步骤。例如“密码正确时可以进入首页”“网络异常时可以重新提交”，失败报告一眼就能看懂影响。名字清楚后，非测试作者也能参与判断这条保障是否仍值得保留。

当测试真正对应用户能感知的承诺，维护它就不再是额外工作。每一次变更前的绿灯，都是在提醒我们：关键路径刚刚又被认真地走过一遍。
