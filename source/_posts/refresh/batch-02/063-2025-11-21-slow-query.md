页面慢的时候，人很容易先怪网络，接着怪服务器，最后把希望寄托在“加一个索引”上。索引确实经常有用，但它不是给数据库贴上的加速贴纸。一次慢查询真正值得做的，是先看清它究竟在等什么：是在读取太多数据、在排序、在和别的表连接，还是其实请求根本没有走到数据库。

<!-- more -->

我见过最常见的误会，是后台列表打开要四五秒，大家立刻问“索引是不是没建”。后来查下来，SQL 只用了几十毫秒，真正慢的是接口查完后又逐条补了十几个关联信息。这个例子不说明索引不重要，反而说明先测量更重要。没有一段实际 SQL 和实际耗时，任何优化都只是猜谜。

## 从用户的一次等待开始

先把问题说得具体一点。不要写“列表页很慢”，而要记下：哪个页面、带了什么筛选条件、数据量大约多少、首次打开和翻页是否都慢、哪个账号或时间段更明显。然后从浏览器 Network 面板看接口耗时，再在服务端日志里确认请求什么时候进来、SQL 花了多久、序列化和网络传输各花了多久。

这样会得到一条简单的链路：浏览器等待 3.2 秒，其中服务端 2.8 秒；服务端里有一条 SQL 用了 2.4 秒。到这一步，才值得进入数据库。若 SQL 只有 30 毫秒，应该回头查循环请求、图片、缓存或服务端代码；若 SQL 真慢，也不应急着改语句，先保存原样，避免在反复试验时丢掉现场。

## 先问数据库“你是怎么做的”

大多数数据库都能通过执行计划告诉我们查询的大致路线。它不需要一开始读得很深，只要先看几个朴素信号：扫描了多少行、用了哪个索引、是否出现全表扫描、是否在临时排序、是否把不必要的列都取回来了。执行计划像导航记录，告诉你车走了高速还是在小巷里绕圈。

例如，一个常见列表查询会按 `created_at` 倒序、再按 `status` 筛选。如果表已经有几十万行，却没有能支持这两个条件的索引，数据库可能只能先找一大批记录再排序。另一个坑是写了 `WHERE DATE(created_at) = ...` 这样的函数包裹；看起来方便，却可能让原本的时间索引派不上用场。把条件改成时间范围，往往比新增复杂索引更稳妥。

```sql
-- 不利于使用 created_at 索引的写法
WHERE DATE(created_at) = '2025-11-21'

-- 更容易利用范围索引的写法
WHERE created_at >= '2025-11-21 00:00:00'
  AND created_at <  '2025-11-22 00:00:00'
```

## 索引不是越多越安心

索引会占空间，也会让插入和更新多做一些工作。给每一列都加一个索引，可能让查询仍然不快，写入反而变慢。更可靠的思路是从真实的高频查询出发：它用哪些条件过滤、按照什么顺序排序、最终需要哪些字段。把这些信息写在一起，再和执行计划对照，才知道是否需要单列索引或组合索引。

组合索引尤其容易让人困惑。可以把它想成按“省份—城市—姓名”排好的电话簿：查某个省很快，查某个省里的城市也很快，但直接找所有叫张三的人未必快，因为第一层顺序没用上。具体的数据库规则会有差异，实践中最安全的方法仍是：改前看计划、改后用相同数据测一次，不要只凭别人博客里的结论照搬。

## 常见的慢，不止发生在 SQL 里

还有几种很值得顺手检查的情况。第一是一次取回了远超过页面需要的数据，例如列表只显示二十条，却 `SELECT *` 取出长文本、附件信息和大字段。第二是 N+1 查询：先查到二十条订单，再为每条订单查一次用户和商品。第三是分页越来越靠后时越来越慢，因为数据库不得不跳过大量旧记录。第四是锁等待，查询本身不复杂，却正好碰上一个长事务占住了资源。

这些问题的共同点是，它们都能通过记录数量、调用次数和耗时暴露出来。性能优化不必从神秘参数开始。先让日志告诉你“这条请求执行了几次查询、每次返回多少行、最慢的一步是什么”，很多答案会自己浮出来。

## 一个不容易走偏的小流程

1. 用真实但脱敏的条件复现一次，记录浏览器、接口、SQL 三层耗时。
2. 保存原始 SQL 和执行计划，不先改代码。
3. 明确是扫描、排序、关联、返回量、分页还是锁导致的等待。
4. 一次只改一个因素：条件写法、索引、返回字段或关联方式。
5. 用同一组数据重测，并观察写入是否受到副作用。

慢查询并不总要被“优化成极限”。一个后台一年只打开两次的报表，花一秒半也许完全可以接受；一个每次打开首页都会跑的查询，则值得认真照顾。知道哪一种是用户真正的等待，才是性能工作最开始的判断力。

## 优化前，也给自己留一份基线

做性能改动时，最好把“原来多慢”留下来。记录查询条件、数据量、执行计划、平均和最慢耗时，再记录改动后的相同指标。这样不仅能证明优化是否有效，也能避免一种常见情况：为了省几十毫秒引入了难懂的 SQL，后来数据量变化后收益不见了，维护成本却一直留着。

基线还会提醒我们区分偶发和持续。某次测试环境正好有批量任务在跑，出现一次尖峰，并不一定说明常规查询需要重构；反过来，平均值看起来不高，但 P95 或最慢的一小部分请求让真实用户一直等待，也不能被平均数掩盖。对小项目来说，不必搭一整套复杂指标，只要能定期看见“慢的是哪条、在什么条件下慢”就已经很有价值。

优化后别忘了重新回到使用场景里点一点。查询快了，排序是否仍正确？分页会不会漏项？缓存是否让用户看到旧数据？性能和正确性从来不是二选一。一次好改动应当让用户更快到达正确结果，而不是只让一份基准测试更漂亮。

如果暂时不能改代码，也可以先做一点务实的缓解：为重报表加明确的时间范围，限制一次导出的最大行数，把非实时统计放到后台生成，或在页面上说明预计等待时间。性能问题不总要靠一次大改解决。先让用户少等一点、让系统少承受一点，也是在为后续更稳的优化争取空间。
