密码和密钥：别把它们留在仓库

有一次帮朋友看一个小项目，问题并不复杂：项目跑不起来。打开仓库后才发现，真正能让它连接数据库的账号密码只躺在某个人电脑上的配置文件里；另一个更糟的版本，是密码直接写在代码里，随后又被提交到了远端。两种做法看起来相反，一个是“谁也拿不到”，一个是“谁都可能拿到”，本质上都是把重要信息交给了运气。

密码、令牌和密钥常被一起叫作“配置”，但它们并不只是普通配置。普通配置可以是页面每页显示多少条数据、接口地址的前缀；而一把 API Key、一段数据库密码、一个私钥，拿到的人可能就能读数据、发消息，甚至发布新版本。把它们和普通代码混在一起，后面总会遇到两个问题：该用的人找不到，不该看的人却看得到。

先分清手里的是什么

我现在会先做一个很朴素的分类。第一类是账号密码，例如数据库用户、第三方平台登录账户；它们通常可以人工登录或由程序使用。第二类是令牌，例如 GitHub Token、机器人 Token、访问某个云服务的 API Key；它们一般权限更明确，也更适合定期失效和重发。第三类是密钥文件，例如 SSH 私钥、签名证书；它们往往不能只靠“改个密码”解决，一旦泄露需要立即替换。

分类不是为了写一张漂亮表格，而是为了知道出问题时该做什么。数据库密码泄露，先改密码并查访问日志；一个有写权限的 Token 泄露，要先撤销它，再检查它做过的操作；私钥被上传，则应当把旧密钥视为已经失效，生成新密钥、更新使用位置。不要因为仓库后来删掉了那一行，就以为事情结束了。Git 的历史、缓存、fork 和本地克隆都可能已经留下副本。

仓库里应该留下什么

一个可交接的小项目，通常需要三个文件，而不是一个“万能配置”。第一个是 .env，只放本机或部署环境真正使用的值，并且写进 .gitignore。第二个是 .env.example，提交到仓库，保留变量名和安全的示例值，让新成员知道需要准备哪些东西。第三个是简短的说明，例如 README 里的“如何获取测试账号”和“哪些变量不能发到群里”。

让“拿到配置”成为一条正常路径

许多泄露并不是有人故意粗心，而是对方卡在“项目怎么启动”这一步。为了赶进度，他把自己的 .env 直接打包发出去；或者新同事把配置贴进群聊，后来又被转发。解决方法不是反复提醒“注意安全”，而是给出不绕路的获取方式。

我会在项目说明里写清楚：开发环境的非敏感配置在哪里；测试账号向谁申请；生产环境的配置由哪个部署平台保存；需要临时权限时如何申请、多久收回。哪怕只有两个人维护，也值得留下这几句话。它让大家知道安全不是“会不会记得”，而是流程的一部分。

同时，权限要尽量小。用于本地调试的 Token 不需要拥有删除线上数据的能力；用于读取统计的账号不需要创建新用户；一个临时脚本结束后，其令牌也不该一直有效。最小权限听起来像大团队的术语，其实就是少给一把没必要的钥匙。钥匙越少，遗失时要担心的门也越少。

真提交过怎么办

如果密钥已经进了远端仓库，第一步不是急着改历史，而是立即撤销或轮换。这是最能降低风险的动作。第二步再删除当前文件里的值，并检查提交记录、构建日志、截图和聊天记录是否也带出了它。第三步才是用工具清理 Git 历史；历史清理能减少后来的人误用旧密钥，但不能保证已经拿到副本的人消失。

事后可以补一个很轻的检查：提交前搜索 password、secret、token、BEGIN PRIVATE KEY 等高风险词；CI 中也可加入密钥扫描。工具会有误报，所以不必把每次提示都当事故，但应当认真确认。比起在出事后翻遍几十次提交，提交前多花半分钟更便宜。

一份放在手边的清单

  • 真实 .env、私钥和证书文件是否被忽略，而示例文件是否已提交？
  • 新成员能否在不索要别人电脑文件的情况下拿到开发所需配置？
  • Token 是否区分开发、测试、生产，且权限没有超过用途？
  • 一旦泄露，是否知道去哪里撤销、轮换和查看日志？
  • 最近一次离开项目的人，是否仍保留不需要的访问权限？

安全并不靠把所有东西锁进抽屉。真正可靠的状态是：需要的人能通过正当路径拿到恰好够用的权限，不需要的人没有机会顺手看到，而任何一次意外都能被快速收回。对个人项目来说，这已经是一种很舒服的秩序。

在交接和离开时再检查一次

密钥管理最容易出问题的时刻，往往不是写代码的时候，而是交接、换电脑、结束合作的时候。有人换了电脑，便把整个配置目录压缩到网盘；有人离开项目，账号没有及时撤销；有人接手发布，发现只有旧同事知道部署平台的二次验证在哪台手机上。平时看起来顺手的捷径，在人员和设备变化时会突然变成单点风险。

所以每隔一段时间，不妨做一次“假装今天换人维护”的检查：一台没有历史文件的电脑，能否按说明启动项目？现有管理员是否仍然需要全部权限？如果某个 Token 今天被撤销，是否知道哪些脚本、构建或服务会受影响？这类检查不需要频繁，但每次做完都会让配置从“某个人的经验”变成“项目能延续的能力”。

还有一点很现实：不要把安全做成只有最懂技术的人才能完成的事。变量名清楚、申请路径明确、异常联系人可见，都会降低别人为了赶进度而走捷径的可能。一个人不必记住全部密钥在哪里，只要知道该向哪里申请、哪些内容绝不能复制、发现异常后先做什么，就已经帮助项目避开了很多不必要的风险。
