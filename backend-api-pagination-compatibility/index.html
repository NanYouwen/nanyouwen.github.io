接口分页的兼容性，不只是一句 limit 和 offset

列表页很容易被当成最简单的页面：给接口两个参数，前端拿到一页数据，再点下一页。数据少的时候确实如此。可当用户一边翻页，另一边又有人新增、删除或更新记录时，分页会开始露出性格：上一页最后一条在下一页又出现了，或者某条记录悄悄不见了；越翻到后面越慢；搜索条件一变，页面还停在第九页，结果只剩一个空白。

分页真正要回答的不是“每页多少条”，而是“用户正在看的这段数据是什么顺序、在数据变化时允许发生什么、前后端怎样表达还有没有下一页”。先把这几个问题讲明白，具体用 offset 还是 cursor 才有判断依据。

两种常见方式，各有适合的地方

limit + offset 最直观：取二十条、跳过前四十条，就是第三页。它适合后台管理、数据量不大、需要跳到指定页码的场景。用户能看到“第 3 / 12 页”，也能快速跳到最后一页。代价是 offset 很大时，数据库可能仍需要跳过前面很多行；数据持续变化时，位置也容易移动。

cursor 分页则更像“从我现在看到的最后一条之后继续”。接口返回数据的同时给一个游标，下一次把游标带回去。它常用于时间线、消息流、操作日志等不断增长的列表，因为顺序更稳定，越往后通常也不会越来越慢。它不擅长直接跳到第 87 页，也不天然告诉你总页数，所以不该为了时髦强行替代普通分页。

不管选哪种，都要有确定的排序。只按 created_at 排序看似够用，但两条记录在同一秒创建时顺序可能不稳定。实际项目里常会补上唯一 ID 作为第二排序条件，例如先按创建时间倒序，再按 ID 倒序。这样翻页时，前后端才在谈同一条队列。

返回数据时别让前端猜

一个友好的分页响应，不止有 items。offset 场景可带上 page、pageSize、total；cursor 场景至少应有 nextCursor 和 hasMore。字段命名不必追求唯一正确，但含义必须清楚：total 是筛选后的总数还是全部总数？nextCursor 为 null 是没有下一页，还是系统暂时算不出来？这些细节写进接口文档后，前端才能正确设计空态和按钮。

例如，用户切换了筛选条件，页面应当回到第一页或清空当前游标，而不是继续拿旧条件的第九页去请求。用户快速连续点击“加载更多”时，要防止同一游标发出多次请求；网络慢时还需要显示正在加载，避免数据插入顺序混乱。分页接口很小，交互的边角却很多。

数据变化时，先约定体验

列表不是账本快照。若有人正在浏览订单，同时有新订单不断进来，你必须决定新数据出现在哪里。后台管理页可以在顶部提示“有 3 条新记录，点击刷新”；消息流可以直接插入，但要避免把用户正看的内容推走；导出报表则应该固定一个查询时间，保证分页结果一致。

不要承诺一个实现不了的“绝不重复、绝不遗漏”。在普通业务列表里，允许刷新后少量位置变化，往往比为了绝对一致引入复杂事务更划算。关键是让用户知道发生了什么，并让接口排序和前端刷新策略保持一致。

一个上线前检查表

  • 每个列表是否有稳定且文档化的默认排序？
  • 改搜索、筛选、排序后，页码或游标是否会重置？
  • 空列表、最后一页、网络失败、重复点击时，界面分别显示什么？
  • 总数是否真的有必要实时计算，还是可异步或近似？
  • 数据变动时，用户会看到刷新提示、自动插入，还是固定快照？

分页不是炫技，它只是让用户从一堆数据里顺畅地找到下一段。把顺序、边界和变化讲清楚之后，limit、offset、cursor 都只是合适的工具，而不是后期不断修补的起点。

兼容老接口时，宁可多说一句

分页规则一旦被客户端使用，修改时要格外小心。把原来的 page 改成 cursor，不只是服务端少改几行 SQL；旧版前端、导出脚本、第三方调用都可能仍在依赖页码和总数。比较温和的迁移方式是先增加新字段、保留旧字段一段时间，在文档中写明推荐方式和废弃时间，再通过日志确认旧调用是否已经消失。

参数也要给合理默认值和上限。没有传 pageSize 时使用安全默认值；传了几千条时限制最大值并返回清楚提示；传了无效游标时告诉调用者应当刷新，而不是悄悄从头开始。接口越早把边界表达出来，前端越不需要用猜测补漏洞。

最后别忘了把真实的列表交给人试一试。开发者常关注“第二页能不能拿到”，用户更在乎筛选后是否突然空白、回到上一页是否还在原位置、手机上加载更多是否有明确反馈。分页是数据规则，也是交互承诺。后端的稳定顺序和前端的清楚反馈一起存在，用户才会感觉这张列表是可信的。

若列表允许导出，也要写清导出是否遵循当前筛选和排序、是否有单独的大小限制、异步任务完成后如何通知。不要默认导出就是“把所有页拼起来”。导出常常比浏览列表更接近真实的数据需求，它更需要一个固定条件和可追踪的结果。把这些约定在接口旁边写明，分页就不会在需要交付数据时突然失去边界。

此外，给分页请求加上必要的日志也很有帮助：筛选条件、排序、页码或游标、返回条数和耗时。它们能在用户说“我找不到刚才那条”时快速还原当时看见的范围。没有这些信息，排查往往会退化成反复刷新和猜测；有了它们，问题会清楚得多。

这样设计后，列表即使面对持续新增的数据，也不会显得不可预测。用户知道自己看到的顺序，开发者知道如何还原问题，分页才真正成了一段可靠的浏览体验。

一个小场景可以检验约定是否完整

比如用户筛选“本月待处理”，浏览到第二页后有一条新记录插入最前面。此时接口若没有稳定排序，第二页可能重复一条或漏掉一条；若使用游标，前端又要知道游标对应的是哪组筛选条件。把这个场景写成测试用例：固定排序字段、翻页时保留筛选、刷新后明确提示列表可能已更新。它能把分页从抽象参数变成用户真正会遇到的变化。

对无限滚动也一样。加载中、到底了、失败可重试、切换筛选后重置位置，这几种状态都应有清楚反馈。用户不必理解 cursor 或 offset，但应该始终知道自己在看一段连续而可信的内容。
