RAG 知识库的第一步：先决定哪些资料不该放进去

我第一次搭知识库时犯过一个很自然的错误：看到文件夹里有很多资料，就觉得资料越全，回答就会越好。真正运行几次以后才发现，旧通知、草稿、重复导出和权限不明的附件混在一起，模型得到的不是完整背景，而是一堆互相冲突的线索。RAG 的第一步并不是选择向量数据库，而是决定什么值得被检索、什么应该留在原处。

先问资料要解决什么问题

知识库不是电脑硬盘的镜像。放进去的每一份资料，都应该能回答一个实际问题：它服务谁，什么时候使用，使用者需要从中做什么决定。如果只能说“以后可能有用”，却说不出检索场景，那它更适合先进入待整理区，而不是直接进入正式知识库。

我会给资料写一张很短的登记卡：名称、来源、负责人、适用范围、最后更新时间和预计失效时间。登记卡看起来比上传按钮麻烦，但它能避免一个常见误解：文件存在，并不代表它应该被系统当成事实。尤其是会议纪要、个人草稿和临时方案，它们的可信度和正式说明完全不同。

四类资料最好先分开

第一类是稳定事实，例如已经发布的接口约定、操作流程和公开规范；第二类是阶段性资料，例如本季度方案、正在执行的计划；第三类是参考材料，例如教程、案例和讨论记录；第四类是个人工作痕迹，例如草稿、聊天摘录和未确认结论。它们都可能有价值，但检索时不能拥有同样的权重。

“把所有文件都丢进知识库”这个场景里，我会先把第四类资料隔离出来，再决定是否允许检索。一个没有确认过的猜测，如果和正式流程一起被召回，模型很容易把语气相近的两段内容拼成一个看似确定的答案。知识库的质量，很多时候取决于它能否保留“不确定”的标记。

权限不能等导入之后再补

如果一份资料只有少数人可以看，就不能因为接入 RAG 方便而把它放进所有人共享的索引。权限至少要在资料进入索引前确认一次，并且要考虑权限变化后的删除和重建。只在回答阶段隐藏链接，不等于底层检索没有泄露风险。

我会把资料权限分成公开、团队、项目和个人四层，并给每个文档附上负责人。这样做的好处不是分类漂亮，而是当有人离职、项目结束或资料过期时，知道应该找谁处理。涉及合同、客户信息、密钥和内部决策的内容，宁可暂时不接入，也不要为了演示效果扩大范围。

一个可以马上做的整理练习

拿一个真实文件夹，先不要接模型，只做三轮筛选。第一轮删除明显重复和空文件；第二轮给每份资料补来源、时间和负责人；第三轮把内容分成正式、参考、草稿和待确认。每轮都保留数量变化，最后写下哪些资料被排除以及原因。

然后挑十份最常用的资料做小范围导入。给它们各写三条问题，观察答案是否能引用正确来源。如果回答经常把草稿当结论，就回到资料标签和检索过滤，而不是先换一个更大的模型。一个小而干净的知识库，比一个什么都有却无法解释的资料仓更适合开始。

我会留下的检查表

  1. 这份资料具体服务哪一种问题？
  2. 来源、负责人和最后更新时间是否明确？
  3. 草稿、参考和正式结论是否有区分？
  4. 谁有权查看，权限变化后如何撤回？
  5. 资料失效时，索引和回答会不会继续使用它？

RAG 的人文部分也在这里：我们不是把人的经验压缩成文件，而是在决定哪些经验可以被别人依赖。越是重要的知识，越应该让来源、时间和不确定性一起出现。先把资料边界画清楚，再谈切分、向量和提示词，后面的系统才有机会真正帮助人，而不是替混乱增加一层自动化。

一个容易被忽略的复盘角度

做完第一次实验后，我会把问题从“答案好不好”拆成几个更具体的判断：资料是否真的相关，来源是否足够新，回答有没有越过资料边界，使用者能不能沿着引用回到原文，以及下一次资料变化时谁会负责更新。这样做的好处是，失败不再只剩下一句“模型不行”，而是能够对应到资料、检索、权限、生成或维护中的某个环节。

RAG 很适合帮助人更快找到已有知识，但它不应该替人决定哪些内容可信。面对重要流程、隐私资料和会带来实际损失的动作，我仍然会保留人工确认。一个好的知识库不是让人完全不思考，而是让人把时间花在判断和取舍上，而不是反复寻找同一个文件。

如果这套做法要交给团队使用，还需要补上最小的使用说明：什么问题适合问，什么问题应该直接找负责人，引用不完整时如何反馈，资料过期时从哪里申请更新。把这些入口写清楚，知识库才不会只属于最初搭建它的人。

实践中还可以每隔一段时间抽查几条回答：把问题、引用和原文放在一起，看读者能否独立确认结论。这个动作很朴素，却能及时发现资料过期、切分错误和权限配置变化。它也提醒我们，知识库的可靠性来自持续维护，而不是第一次导入时的兴奋。

如果抽查发现问题，不必马上全量重建。先保留失败样例，确认是源资料、检索策略还是回答组织出了问题，再做一项小改动并重新验证。小步迭代会让知识库更容易解释，也更容易在出错时恢复。

在团队里推广时，我还会把一次成功和一次失败都留下来，作为后来排查的参照。只有看过失败路径，大家才会知道系统什么时候应该停下来问人，而不是把所有问题都归咎于模型能力。

这也是我愿意把 RAG 写成知识工作流的原因：它让资料、判断和责任都有机会被看见。
