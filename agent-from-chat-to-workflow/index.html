从聊天框到工作流：我理解的 Agent

聊天式 AI 最熟悉的样子，是你问一句，它答一段。它像一个反应很快的对话伙伴：能解释、能改写、能出主意，但通常停在文字里。Agent 则多走了一步。它不只回答“可以怎样做”，还会在允许的范围内把任务拆开、调用工具、查看结果，再决定下一步是否继续。

这听起来像给 AI 装上了一双手，但不要把它想成万能机器人。一个好的 Agent 并不是放开权限后自己到处点，而是一条被设计好的工作流：它知道目标，知道手里有哪些工具，知道什么情况下需要停下来问人，也知道做完后如何留下记录。

四个动作，帮助理解 Agent

我习惯用四个很日常的动作理解它：看、想、做、回看。看，是读取用户给的材料、网页、文件或系统状态；想，是把大任务拆成几个可执行步骤；做，是调用搜索、数据库、日历、代码仓库等被授权的工具；回看，则是检查工具有没有报错、结果是否满足要求、是否需要让人确认。

普通聊天也能完成其中一部分，但它不会天然拿到外部世界的反馈。比如让聊天模型“查一下这周有哪些会议”，它最多告诉你如何查；让一个有日历读取权限的 Agent 完成同一任务，它可以读取日程、按时间整理、把冲突标出来。关键不在于它更像人，而在于它能把语言和具体行动连起来。

工作流比角色名字重要

许多 Agent 演示喜欢给角色取很酷的名字：研究员、规划师、执行官。名字可以帮助理解，却不能替代流程。真正需要写清的是：输入是什么；每一步允许使用哪些工具；产物如何传给下一步；发生错误时重试、换方案还是交给人；什么条件算完成。

以“整理一份竞品资料”为例，一个朴素流程可以是：先读取指定网页和文件；把每个结论附上来源；按价格、功能、限制分类；列出资料不足的部分；最后生成一份供人审核的表格。它不需要复杂地让五个 Agent 相互聊天。只要步骤清楚、每一步都可检查，一个 Agent 也能做得很稳。

工具权限决定边界

Agent 之所以值得谨慎，是因为它可能真的能做事。读取文件和删除文件的风险完全不同；草拟一封邮件和直接发出邮件的风险也不同。设计 Agent 时，应该先列权限，而不是先列它能完成的炫酷任务。它是否只能查看？能否下载？能否修改？是否可以对外发送？每一层都应有明确答案。

一个实用原则是最小权限。测试阶段只给测试数据和只读权限；需要修改时先生成预览或差异；涉及付款、外发、删除、权限变更时必须等人确认。这样，Agent 即使理解错了任务，也不会一口气造成很大的影响。

让它在合适的时候停下

“遇到不确定就问人”听起来简单，实际要给出具体触发条件。比如检索不到可信来源、工具连续失败两次、金额超过某个阈值、结果会覆盖已有内容、任务目标有冲突时，都应该停止而不是继续猜。停止不是能力不足，而是流程在保护人和数据。

因此，第一次尝试 Agent 时，不妨选一个低风险、结果容易验证的任务：整理一个公开网页列表、把会议纪要转成待办草稿、给本地文件做分类建议。先把看、想、做、回看这四步走通，再逐渐增加工具和权限。Agent 的价值不是替你把一切自动化，而是让一条原本需要不断切换工具的工作，在可控范围内顺起来。

给第一次试验留下一张记录

跑完一个 Agent 任务后，不妨记下它读了哪些资料、调用了哪些工具、哪一步花时间最长、哪些结果需要人工改正。这不是为了给工具打分，而是为了判断它是否真的减少了切换成本。有时它只节省了两分钟，却引入了五分钟核对，那就说明流程还不适合自动化；有时它没有直接完成工作，却帮你把资料和待办理顺，也已经有价值。

还可以故意准备几个异常情况：没有权限、网页打不开、资料相互矛盾、任务目标不完整。看 Agent 是不是会停下来说明问题，而不是默默跳过或编造结果。一个系统在顺利时看起来都差不多，真正的差别常出现在它遇到障碍时如何处理。

当这份记录逐渐积累，你会得到比“某某 Agent 很强”更有用的认识：在自己的环境、资料和权限下，它适合替你跑哪一段，哪一段仍应由人把关。这个边界越清楚，自动化就越稳，也越不容易让人失望。

一个朴素的完成定义

第一次做 Agent 工作流时，最好把“完成”写得很具体：是否已经读完指定范围；是否成功调用了需要的工具；是否输出了可核验的结果；是否把无法处理的项列出来；是否没有越过权限边界。不要只用“看起来不错”判断。完成定义越清楚，失败也越容易定位。

例如整理会议纪要的 Agent，完成不等于生成了一篇长总结，而是每条待办都有来源、负责人和截止日期；没有负责人时标为待确认；没有权限访问的附件不假装看过。这样的标准既能让人审核，也能让 Agent 在资料不足时知道该停在哪里。

当任务的完成定义可被人读懂，Agent 才真正进入工作流，而不只是换了一种更会说话的聊天框。

开始时不妨把 Agent 的输出放在一个可回看的地方，而不是只留在聊天记录里。无论是任务清单、变更预览还是简短报告，只要人能看到它做过什么、还缺什么，协作就不会因为一次会话结束而失去上下文。

这也是为什么好的 Agent 不该只追求动作数量。它留下的计划、证据和结果，应该让后来接手的人也能理解；自动化若不能被人看懂，就很难真正融入团队工作。

先从低风险的小任务开始

第一次尝试时，可以让 Agent 帮忙整理一组公开链接、把会议记录归成待办草稿，或检查一份文档里是否缺少固定章节。任务范围小、输出容易核验，即使判断不完整也不会造成外部影响。等到输入、工具、检查点和交接方式都跑顺了，再考虑让它参与更长的工作流。先建立可验证的成功经验，比一开始就要求它替人完成整件大事更可靠。
